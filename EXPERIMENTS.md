# HEADGREEN coordinator experiment — 2026-11-08

This public disposable repository contains only synthetic changes and tests. It does not run LearnCard's real E2E suite. `Test` and `E2E` are GitHub Actions-owned required checks, with HEADGREEN, max three concurrent build entries, max three merge entries, minimum two, and a one-minute wait. Experiments were sequential and used synthetic branches. The coordinator and four-job suite are experimental, not production-ready.

## Evidence

- Initial three-PR batch: [head passed](https://github.com/learningeconomy/codex-headgreen-batch-prototype-20261106/actions/runs/42507221512) and three PRs merged, but [both](https://github.com/learningeconomy/codex-headgreen-batch-prototype-20261106/actions/runs/42507219329) [prefixes](https://github.com/learningeconomy/codex-headgreen-batch-prototype-20261106/actions/runs/42507220502) later timed out and ran redundant suites. This was not a net reduction.
- Single PR: [the suite passed](https://github.com/learningeconomy/codex-headgreen-batch-prototype-20261106/actions/runs/42507473719) and the PR merged after the minimum-group wait.
- Intentional shard failure: [the combined E2E gate failed](https://github.com/learningeconomy/codex-headgreen-batch-prototype-20261106/actions/runs/42507629073); failing PR #31 remained unmerged. Earlier PRs ran fresh fallback suites and merged separately.
- Removing a middle PR: [the old head rejected changed membership](https://github.com/learningeconomy/codex-headgreen-batch-prototype-20261106/actions/runs/42508060814); a [rebuilt SHA passed its own suite](https://github.com/learningeconomy/codex-headgreen-batch-prototype-20261106/actions/runs/42508197388), and the removed PR did not merge.
- Four PRs / three build slots: [first three](https://github.com/learningeconomy/codex-headgreen-batch-prototype-20261106/actions/runs/42508469775) and [fourth](https://github.com/learningeconomy/codex-headgreen-batch-prototype-20261106/actions/runs/42508540749) ran one synthetic four-job suite per batch. The two obsolete prefix jobs ended as failed required checks after merge, without starting suites. Waiting coordinators still consumed runners.
- Simulated API outage: [after a bounded wait, a fresh suite passed](https://github.com/learningeconomy/codex-headgreen-batch-prototype-20261106/actions/runs/42508805302). A fallback is not a reused proof.
- Head cancellation: [all four heavy jobs were canceled and E2E failed](https://github.com/learningeconomy/codex-headgreen-batch-prototype-20261106/actions/runs/42509900191); neither PR merged on that run. After manual dequeue of the canceled head, [the remaining PR passed its own suite](https://github.com/learningeconomy/codex-headgreen-batch-prototype-20261106/actions/runs/42509898944) and merged.
- Arrival while running: original revalidation produced two failures and removed a healthy PR: [old head](https://github.com/learningeconomy/codex-headgreen-batch-prototype-20261106/actions/runs/42509244495), [new head](https://github.com/learningeconomy/codex-headgreen-batch-prototype-20261106/actions/runs/42509333551). First correction let the original prefix merge but [incorrectly failed](https://github.com/learningeconomy/codex-headgreen-batch-prototype-20261106/actions/runs/42510363016) the unchanged later SHA after predecessor merges. After requiring exact SHA and independently verified predecessor merge commits, [the original head](https://github.com/learningeconomy/codex-headgreen-batch-prototype-20261106/actions/runs/42510797637) and [late arrival](https://github.com/learningeconomy/codex-headgreen-batch-prototype-20261106/actions/runs/42510884515) each passed and all three PRs merged. Two suites were necessary in this changing batch.
- HEADGREEN affects every required check: an intentionally [failed prefix `Test`](https://github.com/learningeconomy/codex-headgreen-batch-prototype-20261106/actions/runs/42511197276) was followed by a [passing combined head](https://github.com/learningeconomy/codex-headgreen-batch-prototype-20261106/actions/runs/42511199258), and both PRs merged. This is an explicit policy tradeoff, not just an E2E optimization.

## Limits and decision

A polling job consumes a runner per waiting candidate, can starve a constrained runner pool, and still generates failed obsolete checks. It does not implement distributed leasing; independent elections, arrivals, retries, API inconsistency and fallback may start duplicate suites. Queue limits are manually configured because the ordinary Actions token cannot read queue configuration; drift must fail safe. Revalidation is a read, not an atomic queue lock. No full LearnCard E2E, attacker-controlled pull request, exact concurrency quota, app-bound production gate, merged-prefix downstream automation, or realistic slow-suite load was tested. Equivalent-input proof reuse remains separate and was not implemented. No production queue settings were changed.

The synthetic results support further work but do not establish production readiness. Evaluate the changed guarantee for all required checks and design a trusted coordinator, current-SHA app-bound gate, capacity-aware wait/cancel strategy, configuration validation, failure recovery, and rollback before any LearnCard HEADGREEN rollout.
